# Verification

## Offline acceptance

Run `./scripts/check.sh`. The behavior checks compile the production pricing, comparison-capture, session, price-change history, price-table grouping, suppression, manual-watch, and AutoRetainer-handoff code directly, without Dalamud or a game process.

Checks cover quality and ownership filters, single subtraction, price bounds, complete responses, stale and conflicting data, Stop, restart, timeouts, changed listing identity, sequential acknowledgement, and AutoRetainer suppression ownership. Package checks read the assembly metadata without loading the plugin. They require `AutoMarketbuddy`, version `1.2.0.0`, and API 15 in the source manifest, package, and catalog.

Sale-history fallback checks cover the toggle off (leave unchanged, no history read), toggle on (newest same-quality sale minus undercut, confirmed once), quality/mannequin/item filtering, no usable sale, a missing history packet timing out instead of reusing a price, and reuse of a cached empty-market decision on the next retainer.

Empty-market checks cover an item with no competing listing and no offerings packet. The capture accepts the empty result only when the game searched that item, the Compare Prices request changed the search proxy (a new request id or a new proxy state), the result window belongs to that request, and it stayed open for a one-second grace period. A stale search of the same item, a window from before the request, a non-zero count, or a window inside the grace period does not count as empty. The run reports "No competing listing of the same quality.", cancels its editor, and continues to the next item without setting a price. The checks cannot prove that the game opens the result window for an empty market or that it changes the proxy request id for Compare Prices; the owner test checks those.

Cache checks cover Preview-to-Apply reuse, duplicate listings in Preview, cross-retainer targeting, item/quality misses, refresh, five-minute expiry, expiry before confirmation, context changes, and Stop. Cache hits do not extend expiry or repeat the market comparison. Missing or expired entries use the normal in-game comparison path.

AutoRetainer handoff checks cover the opt-in gate, one request per retainer pass, duplicate callbacks, a busy run, a mismatched retainer name, a missing retainer menu, a sale list that appears before its container is ready, a sale list that never opens, a retainer with no listings, Stop, mode-off during a run, AutoRetainer unload, request failure, release failure, disposal, and exactly one release. They also check retainer identity after list loading and disposal before AMB owns the handoff. Menu, list, and session waits after the handoff are bounded. A pending request waits for AutoRetainer's callback or an observable stop; the API has no cancellation endpoint. The fake market checks ordering and release counts; it does not prove the native `SelectString` callback, AutoRetainer's own task scheduling, or the live retainer menu.

Price-change history checks cover one row for each observed change, no duplicate after a repeated observation or a later run, the AutoRetainer handoff path, retention across runs, preview records, and manual observation. The manual-edit check models a price editor that hides the sale list, a confirm click, and a container reload that still reports the price from before the edit; it requires one row for the confirmed price, no row for a cancelled edit, and no reverse row while the container stays stale. A manual-comparison check models the price editor with the market result window open, records the proposal and its log line, fills the comparison cache, and then runs Apply for the same item without another Compare Prices call. A second check requires an empty passive comparison to leave the cache empty. A third check keeps the passive path inactive while a run owns the windows and its packets. A Clear check requires an empty table and no new baseline log line while the sale list stays open, and one row with the known old price after a later change. Table checks cover unchanged listings, six identical transitions merged into one row with count six, a different price kept separate, and a confirmed proposal that changes the same row from proposed to applied. Order checks compare the processing order with the sale list's displayed slot order and cover listings that the display list does not mention. They cannot prove that `AgentRetainer.SellListEntries` matches the live sale list, that the game reports the confirm click with the parameter of the Confirm button, that the price reported after a reload is current, or that the result window and offerings packets belong to the manual comparison; the owner test checks those.

The adapter compiles against the selected installed Dalamud and FFXIVClientStructs assemblies. Compilation cannot establish that native signatures, event registrations, or server acknowledgement behave as expected in the game.

UI and chat commands enter the same queue. The framework drains that queue before advancing the session. Normal unload runs on the framework thread because `CanUnloadAsync` is false. Shutdown releases ownership without native cleanup if the framework is already unavailable. Update, draw, command, and market-event registrations are removed on disposal.

## Owner acceptance

1. Keep the installed plugins and restored configuration unchanged until a development test is explicitly arranged.
2. Build with `AMB_PACKAGE_DIR=/tmp/amb-owner-test ./scripts/check.sh`.
3. Load that DLL through Dalamud's development-plugin mechanism in an owner-controlled session. Keep companion automation disabled.
4. Open a retainer sale list with known HQ and NQ listings. Sort the list differently from inventory order.
5. Run `/aundercut preview`. Check the reported slot, item, quality, current price, and proposed unit price against the game. Check that the price-change rows follow the sale list from top to bottom.
6. Confirm that preview leaves every listing price and quantity unchanged. Inspect the log for unsupported-control errors.
7. Change one listing price by hand in the sale list. Check that one history row shows the old and new price, that a second observation does not add another row, and that the log has one `Price baseline:` and one `Price change:` line for that retainer, slot, and item. Also open the price editor, type a different price, and cancel: no row should appear.
8. With the sale list open, check that unchanged listings already appear in the table with their current price. Then open the price editor for one listing and click Compare Prices. Before you confirm anything, the table should show the proposed price as a dim row, and the log should contain one `Comparison captured:` line. Cancel the editor: the proposal stays dim. Repeat for the same listing and confirm the proposed price: the same row should become an applied change with no second row. Click Clear: the table should stay empty while the sale list stays open, and the log should have no new `Price baseline:` lines. Close and reopen the market result window, then run Apply for that item within five minutes: the trace should show Cache and no new Compare Prices request.
9. Repeat preview and use Stop while waiting for comparison data. Close the control window during another preview.
10. Close the sale list during preview. Verify that the run stops and does not operate on another retainer.
11. Enable "Exit retainer when finish" and complete a run. The sale list should close, the retainer menu should select Quit, the farewell dialog should advance without a click, and the retainer list should return within five seconds.
12. Unload and reload the development plugin. Verify that one command and one update subscription remain active.

Preview still opens native editors and comparison windows. Its control path never sets or confirms a price. An empty market is accepted only after the game opens the result window for that item, issues a new search request, and sends no offerings packet for the grace period. Without that signal, the run stops on the existing deadline instead of trusting cached data.

For later builds, Dalamud's dev-plugin automatic reload can replace manual disable and enable steps. Stage the checked build first. Replace the DLL while the game is idle and AMB is stopped, with no pending confirmation. Dalamud unloads the old instance before loading the replacement. Reload resets the session.

Arrange a separate owner-approved transaction test only after preview passes. Use one low-value listing and check the server-visible result after one price confirmation. Verify that the run continues only after the local listing price matches. A local cache match is not proof of server persistence. A submitted confirmation cannot be cancelled or rolled back by Stop.

For a cache test, Preview one retainer, then Apply within five minutes. Preview should compare duplicate items of the same quality only once. The Apply trace should show Cache and no repeated Compare Prices request. On the next retainer, matching items and quality should reuse the same response. Missing entries should compare in game. After five minutes, Apply should compare again. Each new Preview refreshes the current retainer's entries.

The plugin compares only the first 100 listings returned by the game. It filters retainers registered to the current character; it cannot identify every retainer on other characters or accounts. Avoid manual market interaction during a run. Marketbuddy may stay loaded: each run holds its `Marketbuddy.Lock` interop lock from Start until completion, Stop, failure, or unload, and re-acquires it before opening each price editor. Offline checks cover that hold/release lifecycle with a fake market; the native lock against the real Marketbuddy build still needs the owner test below. Allagan Market may stay loaded: it displays prices and an optional copy button but does not change listings on its own. AutoRetainer is paused through `AutoRetainer.SetSuppressed` for each run and restored on completion, Stop, failure, or unload; a pause already owned by another plugin is left in place. Offline checks cover the pause lifecycle; the real IPC and an older AutoRetainer without it still need the owner test below. The adapter cannot identify every automation plugin.

For a Marketbuddy coexistence test, enable Marketbuddy with its defaults (auto-open compare prices, click-to-set price, auto-confirm), then Preview and Apply. Marketbuddy should not auto-open the price list, paste, or set prices during the run, and should work normally again after the run ends. Also test one listing priced below the target: Apply should raise it to lowest competing price minus the undercut and verify the new local price.

For an AutoRetainer coexistence test, leave AutoRetainer loaded and enable a task or Multi Mode that would normally act on the retainer list. Start Preview with the sale list open. AutoRetainer should not open the retainer list, select a retainer, or confirm a window during the run, and its normal state should return afterward. Repeat with AutoRetainer already suppressed by another plugin and verify that it stays suppressed after the run. With Allagan Market loaded, verify that its retainer overlays and recommended price display do not change the listing or open a game window during Preview or Apply.

For the AutoRetainer handoff, select Preview under "During AutoRetainer" or run `/amb autoretainer preview`. Start the AutoRetainer pass and watch the first retainer. AutoRetainer should wait at the retainer without selecting the next one while Auto-Marketbuddy opens the sale list, reports each listing, closes the list, and returns the retainer menu. AutoRetainer should then continue to the next retainer exactly once. Run Stop during a handoff and verify that the retainer menu returns and AutoRetainer continues. Repeat with Apply only on one low-value listing after Preview passes. If the sale-list menu entry is missing or the list never becomes ready, Auto-Marketbuddy should release AutoRetainer without changing prices. Do not unload Auto-Marketbuddy between its request and the retainer callback; that case can leave AutoRetainer waiting.

For the sale-history fallback, leave the toggle off and Preview an item with no competing listings of its quality: the listing should be reported unchanged with no price submitted, and the run should continue to the next item. Then enable "Use recent sale price when no listings" and Preview again: the result should cite History and propose the newest same-quality sale minus the undercut. This path depends on the game sending the history packet with the same Compare Prices request; the offline checks cannot prove that. If it does not arrive, the run stops on the 30-second deadline without setting a price — report that rather than retrying.

## Compatibility

`InternalName` remains `AutoMarketbuddy`; existing `UndercutAmount` and `WaitDelayMillis` values remain readable. Wait delays are measured in milliseconds and bounded to 250–5000 ms per transition. Each state has a 30-second wall-clock deadline.

`/aundercut start` now previews. Use `apply` explicitly for price changes. The former hidden record, verbose-log, and retainer-check flags did not control reliable pricing behavior and are no longer used. Prices are always checked, and a run sets each price to the undercut target, raising or lowering it as needed. Configuration is saved only after an explicit settings edit.
